Batch 3 · Laboratorio #2 — CNN

Modelos y entrenamiento

Dos arquitecturas, un ciclo de entrenamiento compartido: MLP sobre el vector aplanado, CNN sobre el tensor 2D, ambas verificadas con una prueba de humo antes de gastar tiempo en la búsqueda de hiperparámetros.

Qué se hizo

Se definieron MLP (Flatten + capas Linear configurables) y CNN (bloques Conv2d+BatchNorm2d+activación+Pool configurables, seguidos de FC), un train_model genérico que reutiliza el mismo ciclo para ambas arquitecturas, y evaluate_metrics con accuracy/precision/recall/F1 (macro) vía sklearn. Una prueba de humo de 1 época confirma que ambas arquitecturas entrenan y bajan su loss antes de iterar hiperparámetros en el Batch 4.

Ya visible en la prueba de humo: con un número de parámetros casi idéntico (~106k vs. ~109k), la CNN llega a menos loss de validación tras solo 1 época — primera señal empírica de que compartir pesos y usar convolución local es más eficiente para imágenes que conectar cada píxel a cada neurona.

Decisiones y por qué

Pros del enfoque

  • Ambos modelos exponen los mismos hiperparámetros como argumentos del constructor (activation, dropout, tamaños) — permite que el Batch 4 itere cambiando una o dos variables sin reescribir clases.
  • run_epoch es una única función usada tanto para entrenar como para evaluar (val/test), controlada por si se le pasa un optimizer — evita duplicar lógica de forward/loss entre modos.
  • La prueba de humo usa assert sobre el rango esperado del loss inicial (cercano a ln(10), el loss de un clasificador aleatorio de 10 clases) — falla rápido si el modelo o los datos están mal conectados.

Contras / límites

  • El tamaño espacial tras las capas conv se calcula con 28 // (2 ** n_capas), asumiendo padding=1, kernel_size=3 y pooling de tamaño 2 en cada bloque — no es una CNN totalmente genérica para cualquier configuración arbitraria, pero cubre el espacio de búsqueda planeado para el Batch 4.
  • No hay early stopping ni checkpointing — cada corrida entrena las épocas fijas indicadas; aceptable dado que MNIST entrena rápido y el enunciado pide registrar curvas por época, no el mejor checkpoint.

Investigación detallada: por qué reutilizar un solo ciclo de entrenamiento

Al tener MLP y CNN implementando la misma interfaz (forward(x) -> logits), train_model/evaluate_metrics no necesitan saber qué arquitectura están entrenando. Esto no es solo menos código: garantiza que la comparación del Batch 5 (parámetros, accuracy, tiempo) mide diferencias reales entre arquitecturas y no artefactos de tener dos loops de entrenamiento ligeramente distintos (p. ej. un optimizer.zero_grad() en un lugar distinto).

Impedimentos encontrados

Ninguno — el smoke test corrió en el dispositivo mps disponible en este equipo sin errores de compatibilidad de operadores.

Qué más se podría hacer

  • Early stopping basado en val_loss, si se quisiera ahorrar tiempo de cómputo en la búsqueda de hiperparámetros del Batch 4.
  • Guardar checkpoints del mejor modelo por configuración, en vez de solo el historial de loss — útil si se quisiera re-cargar un modelo sin reentrenar.

Glosario

Smoke test
Prueba mínima y rápida que verifica que el sistema "enciende" — aquí, que ambos modelos entrenan sin error y su loss baja, antes de invertir tiempo en una búsqueda extensa de hiperparámetros.
Macro average (precision/recall/F1)
Promedia la métrica calculada por clase dándole el mismo peso a cada una, sin importar cuántas observaciones tenga — apropiado aquí porque las clases de MNIST están razonablemente balanceadas (Batch 1).
Parámetros entrenables
Suma de elementos de todos los tensores de peso/bias de un modelo con requires_grad=True; se usa en el Batch 5 para comparar eficiencia entre MLP y CNN.
